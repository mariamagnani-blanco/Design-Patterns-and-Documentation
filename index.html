Navigation Pattern System

A working definition of how navigation should behave across Bitso Business, piloted in Settings and intended to scale platform-wide, including the structural patterns, the rules that decide when each control shows up, and a clickable reference prototype so the behavior can be experienced, not just read.

Overview

This covers two different things, and it's worth being clear about which is which before diving in.

  1. Two structural patterns, which decide the overall shape of a navigational surface: a Dynamic Contextual Sidebar for browsing between sections, and a Full-Page Flow for focused, single-purpose tasks.
  2. Three interaction patterns used to move within and between those structural patterns: Back, Breadcrumb, and X. Which one shows up, and where, is decided mechanically by a couple of rules (covered below), not by picking whichever looks right on a given screen.

Grouping and naming (which items belong together, what to call them) is deliberately not covered here.

Pattern documentation

Each rule below includes the reasoning behind it, since that reasoning is as load-bearing as the rule itself.

Structural pattern 1: Dynamic Contextual Sidebar

For browsing between sections of the app.

There's one sidebar with two states:

  • Main state: the top-level product sections. These are plain links, or Accordions for sections with a few shallow children.
  • Contextual state: the same sidebar fully taken over by a section's own sub-navigation. You enter it from a Main-state item and leave it through a "← Volver a la app" control at the top of the sidebar. It's not a modal, not an overlay, and not a second sidebar running in parallel.
RationaleMoving in and out of Contextual state always uses Back, never an X (see Interaction patterns below for why).

Responsive presentation

The rules above don't change by breakpoint, but the sidebar's presentation does. On breakpoints where it can't stay persistently visible (tablet, mobile), it's accessed through a hamburger-triggered overlay drawer instead of a fixed column: tapping the icon opens it over the content, and picking a real destination closes it automatically. Reopening the drawer always shows the current selection still highlighted, which is what lets the Back-vs-Breadcrumb rule work completely unchanged here. It's the same orientation a persistent desktop sidebar gives for free, just one tap away instead of always on screen.

How a new nav item becomes a plain link, an Accordion, or a Contextual Sidebar

This is the same decision the FigJam decision tree below walks through visually. In words, it goes in two steps:

  1. Does this item belong under a section that already exists? If so, it inherits whatever pattern that section already uses. You don't re-decide the pattern per page; a new item under Cuentas personales, for example, just follows however Cuentas personales already works.
  2. If it's a brand new top-level Main-state item, look at its children:
    • No children: a plain Main-state link.
    • 2 to 4 children, all flat: an Accordion in Main state.
    • Many children, or children that need grouping: a Contextual Sidebar.

That third branch is really one rule split two ways, so it's worth stating directly:

AccordionContextual Sidebar
ScopeMain-state onlyFull sidebar takeover
ChildrenUp to 2-4, flatCan be grouped, deeper
NestingOne level onlyNo accordions inside it
RationaleIf a section's children need grouping, or there are more than about four of them, it should be a Contextual Sidebar rather than an Accordion. Accordions never nest another Accordion or a Contextual takeover inside them, since that would blur two patterns into one.

Structural pattern 2: Full-Page Flow

For focused, single-purpose tasks, like a multi-step wizard.

It's a full takeover of the content area:

  • No modals. The flow is its own first-class view, not an overlay.
  • No persistent sidebar. The nav sidebar disappears completely while the flow is open (see the rationale below).
  • A fixed header sub-bar with step progress, pinned above the scrolling content instead of sitting inline with it.
  • You exit with an X, top right, not a Back button. It leaves the flow and takes you back to exactly where it was launched from: the exact screen, captured at the moment the flow started (see Interaction patterns below for why it's an X and not Back).
  • Step navigation inside the flow is separate from exiting it. "Continuar"/"Atrás" (or "Cancelar" on step 1) move between steps in the flow's own sequence, a different control from the ×.
Why the sidebar disappears entirely instead of collapsing to an icon railFull-Page Flow is defined by the idea that attention narrows to the task. A persistent nav rail works against that even if it's non-interactive, because it's still a visible invitation to think about other parts of the product. It's worse if the rail isn't clickable, since then it's a false affordance: it looks navigable, does nothing, and erodes trust in the UI. The ×-to-exit control already does the sidebar's job for as long as the flow is open, so a second, inert reminder of the nav structure is just redundant. A collapsed rail is also a third, undefined state sitting between "full sidebar" and "full takeover," and removing it keeps the two-pattern system unambiguous.
"No persistent sidebar" means the sidebar's content, not its entry pointOn tablet and mobile, where the sidebar is normally reached through a hamburger icon rather than a persistent column, that icon stays visible and tappable even during a Full-Page Flow. This isn't an exception to "no persistent sidebar": the sidebar itself is still never shown by default, exactly like everywhere else. Desktop simply has no equivalent icon to hide in the first place, since its sidebar has no toggle at all. Opening the drawer mid-flow and picking a real destination discards the flow immediately, the same as tapping the X, not a second, competing way to exit.

Interaction patterns: Back, Breadcrumb, and X

What you click to move within and between the two structural patterns above. Which one appears is decided mechanically, never a per-page call.

Back

Back shows up in two places, and it means the same thing in both: you're moving one level toward where you came from, still inside the same task.

  • Between sidebar states, moving from Contextual state back to Main state (see Structural pattern 1).
  • In the content area, as the path header when a leaf's content has exactly one ancestor of further depth. This applies to any leaf, whether it's a Contextual Sidebar item (like Item 2.1 → Card A) or a Main-state Accordion child (like Section B1 → Sub Section).

Breadcrumb

Validated in one place so far

Breadcrumb replaces Back in the content area once a leaf's content has two or more ancestors of depth, for example Item 2.1 → Card A → Deeper Item, or Section B1 → Sub Section → Deeper Sub Item. It's a full trail, and every crumb is clickable, so you can jump straight to that depth instead of stepping back one hop at a time.

Why the switch happens at depth 2, not depth 1At depth 1, a breadcrumb and a back button do the same job, so we go with the simpler control. At depth 2 or more, the breadcrumb earns its keep because there's now an intermediate layer worth skipping straight to. One data structure (the path) drives this, and the header is chosen automatically based on how long that path is.
Important distinctionThis doesn't loosen the Accordion's own sidebar-nesting rule, which is still capped at one flat level in the sidebar itself. The Accordion rule governs what the sidebar can nest; the Back/Breadcrumb rule governs what a leaf's content page can do once you've clicked into it. They're independent of each other, so a leaf under either pattern can have depth in its content without changing which sidebar pattern it belongs to.

This is validated so far in Mis límites → Cuentas personales. It hasn't been built as a shared component yet, but WDSHeader already has both a back-button slot and a breadcrumb slot (they're just toggled manually right now), so we can implement this without new components once a second real case validates it. Full-Page Flows never show a Back or Breadcrumb path header at all; they use the X below instead.

X

X only ever means one thing: leave the Full-Page Flow entirely and return to exactly where it was launched from. It never appears anywhere else in the system.

Why X instead of Back"Back" already has a specific meaning here: moving one level up a navigational hierarchy. Reusing that label for "leave this task flow entirely" would collide with it, since a user couldn't tell at a glance whether they were moving up the nav tree or abandoning a multi-step task. An × is unambiguous: it always means leaving the flow, never a step within it.
